# Inheritance, Polymorphism and Encapsulation in Group 23's Library

## 1. Class Structure and Layouts
We kept things pretty straightforward for the architecture. All eight of our core classes live safely inside the `numcomp` namespace. Early on, we made a major design decision: every single class is completely stateless. 

Basically, they don't store any data members at all. There is only a single `public:` section in each one, so you won't find any `private`, `protected`, or `virtual` keywords cluttering up the headers. We didn't bother writing custom constructors either; the default ones generated by the compiler work just fine for what we need. 

## Why we chose this?

- Zero side effects: You can use the exact same BasicODESolver object to solve ten different equations back-to-back. Because it holds no memory of the previous run, there is zero risk of leftover data corrupting the next calculation.

- Inherent thread safety: If you ever decided to optimize the library to run calculations in parallel across multiple CPU cores, stateless classes don't suffer from race conditions because there are no shared variables being overwritten.

- Honest APIs: When a class is stateless, the function signatures have to ask for exactly what they need upfront. It makes the code incredibly easy to read, debug, and test.

## 2. Encapsulation

You might be wondering how we handled encapsulation if we don't have any private data to hide. 

Well, we still logically grouped related behaviors into specific objects. Take `BasicIntegrator` for instance—it conveniently packages both the trapezoidal and midpoint rules together in one place. We also maintained a strict wall between the interface and the actual working code. All the public declarations sit cleanly in our header files (`include/numerical-computing/*.hpp`), while the messy implementation logic is completely hidden away in the source files (`src/*.cpp`). 

Protecting the caller's data was another huge priority for us. The methods pass arguments securely; for example, the `Interpolator` takes vectors as `const&` so it can't accidentally mutate them, and the `MatrixSolver` explicitly takes copies of matrices `A` and `b` to keep the original variables perfectly intact. If someone passes a bad input—like setting n = 0 or giving an odd number of intervals—the functions reject it right at the boundary by throwing an exception rather than trying to process garbage data and failing silently. Since there is no persistent state being tracked inside the objects themselves, we simply didn't need `private` access modifiers.

## 3. Inheritance

To be completely honest, our custom classes don't inherit from one another at all. It wouldn't really make sense for our setup because each class is just an independent collection of algorithms. 

That being said, we heavily rely on inheritance through the C++ standard library's exception hierarchy to handle crashes. 
* When we throw `std::invalid_argument` or `std::out_of_range`, those actually derive from a broader base class called `std::logic_error`.
* Going a step further up the chain, both `std::logic_error` and `std::runtime_error` ultimately derive from the massive `std::exception` base class at the very top of the tree.

We use this built-in family of exceptions everywhere in the library to gracefully catch mathematical failures (like encountering a singular matrix or dividing by zero) or arrays that go out of bounds.

## 4. Polymorphism

We get real runtime polymorphism completely for free during our error handling. When the program catches an error as a generic `const std::exception& e` and calls `e.what()`, C++ automatically executes the specific virtual function tied to whatever the actual exception object was at runtime. 

There is also a looser, more flexible kind of polymorphism happening with our inputs. By relying on `std::function` for the math parameters, our solvers don't strictly care what you pass them. You can hand the functions a standard C++ function, a lambda expression, or a full function object, and they will process it interchangeably without complaining.
